# ナレッジ記録スキル

作業中に得た再利用可能な知見を構造化して保存する。
同じ問題に再び遭遇したとき、自分や他のメンバーがすぐに答えにたどり着けるようにすることが目的。

## 保存先

環境変数 `KNOWLEDGE_DIR` で指定されたディレクトリに保存する。未設定の場合は `docs/knowledge` をデフォルトとして使用する。

## トリガー条件

以下の場面で、ナレッジとして記録すべきか判断する:

- **デバッグ解決時**: バグの原因特定・解決策を見つけたとき（例: CORSエラーの原因がプロキシ設定だった）
- **未公開の仕様発見時**: 公式ドキュメントに載っていない挙動・制約を発見したとき
- **設計判断の確定時**: アーキテクチャや技術選定の判断を下し、その理由を残すべきとき
- **API/外部サービスの落とし穴発見時**: レート制限、未文書化の制約、ハマりポイントを発見したとき

## 手順

### 1. 既存ナレッジの重複チェック

新規作成前に、必ず既存のナレッジを検索する:

```
Grep で $KNOWLEDGE_DIR/ 配下を検索し、同じトピックの既存ファイルがないか確認
```

- **類似ナレッジが見つかった場合**: 新規作成ではなく既存ファイルの更新を提案する。`updated_at` を更新し、内容を追記・修正する。
- **見つからなかった場合**: 新規作成に進む。

### 2. ナレッジの作成

#### ファイルパスとファイル名

```
$KNOWLEDGE_DIR/{id}.md
```

`id` は内容を端的に表す短い英語のスラッグ（例: `cors-proxy-config`, `nextjs-app-router-cache`）。

#### frontmatter

```yaml
---
id: cors-proxy-config
title: CORSエラーはプロキシ設定で解決できる
description: 開発環境でのCORSエラーの原因と、プロキシ設定による解決方法
tags:
  - cors
  - proxy
  - debug
created_at: 2026-03-10
updated_at: 2026-03-10
---
```

| フィールド | 形式 | 説明 |
|-----------|------|------|
| id | `short-description` | ファイル名と一致するスラッグ |
| title | 日本語テキスト | 知見の要約（1行） |
| description | 日本語テキスト | もう少し詳しい説明（1-2文） |
| tags | YAML配列 | 検索用の自由タグ（英小文字、ハイフン区切り） |
| created_at | `YYYY-MM-DD` | 作成日 |
| updated_at | `YYYY-MM-DD` | 最終更新日 |

#### 本文の構成

```markdown
## 概要

何が起きたか、何を発見したかを簡潔に。

## 詳細

具体的な原因、仕組み、背景情報。
コード例やコマンド例があれば含める。

## 解決策 / 推奨事項

どうすればよいか。具体的な手順やコード。

## 参考

関連リンク、ドキュメント、Issue等（あれば）。
```

本文のセクションは知見の種類に応じて柔軟に調整してよい。上記はガイドラインであり、厳密なテンプレートではない。重要なのは「次に同じ状況に遭遇した人が素早く理解・対処できる」こと。

### 3. 既存ナレッジの更新

既存ファイルを更新する場合:

- `updated_at` を今日の日付に更新する
- 必要に応じて `tags` を追加する
- 本文に新しい知見を追記する（既存の内容は保持する）

## 引数の利用

- `$ARGUMENTS` が指定された場合、記録するトピックのヒントとして利用する
- 例: `/knowledge cors proxy` → CORSとプロキシに関するナレッジを作成
- 引数なしの場合、直前の作業内容から記録すべき知見を判断する
